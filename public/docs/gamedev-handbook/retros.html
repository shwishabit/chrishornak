2. How the process actually worked

Nominal loop: brief → build → gym → Chris plays → verdict via AskUserQuestion → next milestone. That loop did run cleanly on 08-30 and 09-01, and when it ran it was fast: 3 gates in 90 minutes, each with a verbatim verdict.

Actual loop, by phase:

  1. Design ran ahead of play by a wide margin. Four of seven sessions produced no surviving code. The brief reached rev 5b (story, three acts, seven surfaces, art model, commission list) before a guard existed, and rev 6e before one had been played. Panels (imagined, pre-dossier) and grills drove those revisions, not play notes.
  2. Who decided what (from the record):
    • Chris decided: stealth spine; GBC-only controls (caught Shift himself); no alarm object (cut Claude's alarm panels); Legend of Kage camera; two-rule detection ("this encourages you to take down guards silently"); gym format; controls strip; MVP = Training Village; 12-zone order; star = Up+B; Down family; the two-timing fight (mid-play); dead-stays-dead; zone-select screen; the clang; search un-deferred; walk slowdown; run/dash and anti-mash HELD; star-lure over Blow's advice; ROTN as art key (his screenshots).
    • Claude decided (then Chris approved or didn't object): every starting number in tune.ts; gym zone widths and order; the seven-surface system; the three-act world detail and palace; the story (father twist, mercy ending — from the imagined panel round); the art model "generated world, drawn heroes" (explicitly reasoned from Claude's own limits: "Claude = bad painter, excellent engineer of pictures — aim the style at that"); the concept-art commission list; frame-data values; the five guard types; the behavior-tree state machine; guard speeds; win condition ("stated as an assumption; Chris did not object", 08-27).
    • Panels decided: rev 2's escape rule, checkpoints, assist toggle; the 08-31 scope audit shape. These were imagined personas without sourced dossiers (the dossier system arrived 09-21 for SCANDISK).
  3. Gates were AskUserQuestion after Chris played a gym zone via ?col=N. Verdicts were short quotes ("feels good", "looks good", "Feels right"). There is no play log; verdicts live only in CHANGELOG prose.
  4. Verification on Claude's side was tsc --noEmit (pre-commit hook) + headless screenshots. Claude never plays; it only renders.
  5. Model: plan said Sonnet for builds, Opus for m03, never Fable. Both 08-29 sessions ran on Opus 5; build sessions' models are not recorded anywhere in the game's files.
  6. State hygiene: agent.md + CHANGELOG.md + backlog.md updated every session (good), but the workspace-level landscape (README, memory) drifted within days (D192), and the design brief lived in two places (local file + live artifact) that drifted apart on 08-31.

3. What went well (evidence)

  1. The gym. Chris rejected the random layout on 08-30 and the rebuild took one commit (60a53be, 15 min). Every later milestone reused it (zones 11, 13, 14, 15, 16, 4b). It turned "is it fun?" into a walkable checklist and became a standing rule (feedback_game_test_levels_are_gyms.md, agent.md rule 11) that SCANDISK inherited.
  2. On-screen controls strip, updated in the same commit as any button change (rule 10, 4b12d36). index.html today is current with every verb.
  3. tune.ts as Chris's file. All numbers in one place, header says "This file belongs to the designer (Chris)". Live tuning happened where it mattered (camera look-ahead d751e2b, walk speed 13045de, guard speeds).
  4. Chris designed in play, and it landed same-session. The two-timing fight (00:40), dead-stays-dead, the visible windup, the spawn-facing fix — all came from Chris playing for minutes, not from paper. agent.md SWOT: "Chris designed IN PLAY … every change landed same-session with tsc + screenshot evidence."
  5. Hard rules held once written. No Shift after 08-29. Greybox held — no art crept into 00–04. Stealth spine never re-proposed. GBC-only input survived every build.
  6. Milestone-scoped commits + tsc pre-commit + push before the real playtest (08-31, "undo point exists"). The m03 churn is legible in git because each pass was its own commit.
  7. Brief kept in lockstep at gates (rev 6g and 6h republished same URL, read-then-merge after the 08-31 drift scare).
  8. The learning loop produced durable rules: rules 11–13 in agent.md, D141 (doc-blind build), D144 (render-and-read pages), D192 (landscape drift), P18 (gyms). Honest SWOTs every session.
  9. Honesty about art. The page itself says nothing was drawn by hand; Chris's "amateur" verdict on Claude's pixel art was recorded, and the response was "build tools, don't re-attempt painted sprites" rather than more guessing.
  10. The cold-start handoff pattern (RAFTER-BUILD-BRIEF.md §5 "8 traps") worked: the 08-30 session hit none of the 08-29 traps.

4. What went poorly (evidence)

4.1 The AI built the wrong game once and nearly authored it twice

  • 08-29 s1: wrong genre, wrong repo, wrong palette, Shift bound, sandbox localhost — every structural decision was answered by docs the session couldn't read. Chris's "go ahead" did not help because he couldn't see which docs were missing (D141, still proposed-awaiting-approval 24 days later).
  • Invented mechanics laundered as Chris's, twice (alarm-panel race, noise radius — archive 08-29 s1 gotcha 6, D142). This is the exact failure Chris's goal names: the game feeling like the AI's.

4.2 Paper outran play, badly

  • ~8.5k words of brief vs 1,315 lines of code. Rev 1→5b in one night, 6→6e in one session — 11 revisions before a guard had been played.
  • The brief carries a three-act world, a palace, a warlord who is your father, a mercy ending, a seven-surface traversal system, 8 background palettes and a 7-piece artist commission list — for a game whose MVP is a training yard and whose v1 "ships rafters + floor ONLY".
  • new-game.md's anti-pattern "Polishing the brief when there is nothing to play" was written 09-17 from SCANDISK. Rafter did it first (08-29 ×2, 08-31 s1) and the lesson was not captured until game #2 repeated it.
  • Chris's own signal on 08-29: "we're making this more complicated than it needs to be" — twice — and the session kept grilling (six rounds).

4.3 Four documents claimed to describe the game

  • [PLAN] block (left "three revisions stale" as "provenance"), BUILD-BRIEF.md, GAME-BRIEF.html, memory. Precedence callouts were "the only thing preventing a wrong build" (archive SWOT). The live artifact drifted ahead of the local file on 08-31 (.pre-merge.bak). README + memory said "NOT BUILT" for 16 days (D192).

4.4 Gates were softer than the plan said

  • m01's locked gate: "Chris messes about for 2 minutes and does not want to stop." Recorded verdict: "a good start with the basics" + "Feel not yet tuned." It passed. The promised tuning session never happened; only one movement number (camera look-ahead) was ever tuned live. The kill switch ("if 01 isn't fun, change the game") was never honestly evaluated.
  • m05's gate ("replays it without being asked") — the one that answers "is this game fun?" — was never reached.

4.5 The 09-01 sprint stacked unplayed work at the end

  • m03 shipped "mechanically right and unreadable" (invisible win, instant restart, mash beats timing) — three defects Chris had to find. The legibility pass then bundled 3 changes in one commit.
  • After m04 passed at 00:58, the session added a system not in the milestone table: 4-state behavior tree, 5 guard types, sleeper, clang, search (which the 08-27 plan explicitly deferred to post-v1). +286/−102 across 7 files at 01:12 am, unplayed. Then a walk-speed retune at 01:16 with a known risk ("gym gaps assume air 72"), also unplayed. Backlog "Now" still opens with "Chris plays the gym end-to-end" three weeks later.
  • guard.ts rewritten 3× in one session. Spiral Detection's "3rd edit" rule was skirted, not tripped, because each rewrite came with a "done".

4.6 The MVP never got built

  • Milestone 05 is the MVP. It has zero commits. The handoff ("fresh session, Sonnet") depended on Chris re-triggering it; the system had no pull mechanism, and 16 days later attention moved to SCANDISK.

4.7 ADHD-unfriendly session shape

  • Sessions ended at 02:20, 02:59, 01:31. The best day was a 90-minute, 13-commit, 4-gate sprint after midnight. Ten open-question cards, plus several "HELD" decisions (run/dash, anti-mash, slide job, perception decay, finite stars) left as live loose ends. The plan estimated 6–9 sessions and got compressed into three late-night bursts followed by silence — the classic hyperfocus-then-drop curve.

4.8 Chris has never played Rafter on a phone

  • No ship script (new-game.md said "write it alongside the FIRST real game"), dist/ stale since 08-30, keyboard-only input, no touch buttons. The GBC-on-phone rule that cost SCANDISK a rebuild round on 09-21 was never applied to Rafter at all.

4.9 Art direction was "locked" twice before any gameplay, and the second lock bent to the tool

  • "Night Watch" locked 08-27 01:56; fully replaced by the ROTN key on 08-29 rev 3 after two more wrong guesses. Then the art model was chosen from Claude's capability ("Claude = bad painter…") rather than from Chris's taste. Reasonable engineering; questionable authorship.

4.10 Tooling friction

  • Cloud container without the workspace (D141/D143). Games/ invisible to bare Glob/Grep (repeated in every doc as a trap). Artifact-vs-local drift. Authored HTML shipped broken twice (D144). Headless screenshots are the only thing Claude "sees" of the game.

4.11 No play log, no learning line, no model log

  • new-game.md step 5 asks for "one play-log line per loop in agent.md (date · build · what Chris felt · the one change)". Rafter has none; verdicts are scattered quotes. No build carries a "This build should tell us ___" line (milestones do carry "Must answer", which is good but coarser). No session records which model/effort ran it, so the plan's model table can't be audited.

5. Where Chris's vision was honoured vs. lost

Honoured (cite)

  • Stealth over movement — Chris overrode Claude's "fluid movement first" on 08-27; rule 5 "Do not re-propose" held through 7 sessions.
  • GBC controls — Chris caught the Shift binding 08-29; "no Shift, no modifiers, no mouse" became rule 8 and every build complied.
  • No alarm object — Claude drafted guards running to alarm panels; Chris cut it: "being seen IS the alarm."
  • Camera = Legend of Kage and detection = cone + fight-noise — both Chris's 08-29 changes, propagated through the brief as design changes, not wording.
  • The gym and the controls strip — Chris's inventions, now standing rules.
  • The Training Village MVP — Chris's framing ("the level shape is the tutorial, never text"), replacing Claude's "one short woods level".
  • The fight — Chris re-designed it live (peak = kill, fall = block), and the frame-data model matches his known taste for SF2/KI timing (user_game_design_style.md).
  • Star-lure noise — Chris's call over the imagined Blow's "fights only" advice.
  • ROTN art key — from Chris's own screenshots after Claude guessed wrong three times in total.
  • Clang, search un-deferred, slow-walk, zone-select — all recorded as Chris's calls in CHANGELOG.

Lost or at risk (cite)

  • 08-29 s1 — none of it was his; all deleted.
  • Two invented mechanics attributed to him (D142).
  • The story, three acts, seven surfaces, palette set, commission list — Claude/panel-authored expansions that Chris approved as reference. By volume the brief is more Claude's than Chris's. The 09-21 SCANDISK finding (D235: "I feel you only using the most basic … I'm disappointed") suggests the inverse risk too: the panel's depth was never checked against his references (Kage, Demon Sword, Shinobi, Tenchu, Halo, Deus Ex — the 08-27 list) mechanic by mechanic.
  • Five guard types + the state machine — proposed and built in one 15-minute window after midnight, unplayed. Whether they are what Chris wants is unknown.
  • The art model was reasoned from Claude's limits, not from Chris's taste.
  • m01 "good start" treated as a pass — the one gate that asked "is moving fun?" got a polite answer instead of a verdict.
  • The m05 handoff — the moment the game was supposed to become his level, the system dropped the thread.
  • Taste profile — user_game_design_style.md (readable base, opponent you read, chains to a big moment, calm pressure) was written 09-21, after Rafter. Rafter was never designed against an explicit taste profile; where it matches (yomi in the duel) it is by Chris's live intervention, not by system design.

7. Lessons → system requirements

Each is phrased for a future game-dev skill/agent system and traced to evidence above.

  1. The system must refuse to write game code when it cannot read the game's canonical brief and agent.md in-session; its only outputs then are a brief and a doc-access fix, and a user "go ahead" does not unblock it. — 08-29 s1, D141.
  2. The system must tag the author of every rule and number: (Chris), (my call), or (panel: <seat>), in the brief, agent.md, tune.ts comments and every build report; anything (my call) gets one AskUserQuestion before it is treated as locked. — D142, invented mechanics; five guard types; win condition "did not object".
  3. The system must keep exactly one design source of truth per game, as a file inside the game's git repo; any live artifact is a rendered copy, republished from the file, never edited ahead of it; older docs are deleted or reduced to a one-line pointer. — four documents, 08-31 drift, .pre-merge.bak.
  4. The system must freeze the brief at the first playable build and reopen it only from a play note; it must show a revision counter and refuse content beyond the current milestone's horizon (no acts, story, palettes or commission lists before the m05-equivalent gate passes). — rev 1→5b, 6→6e; ~8.5k words vs 1,315 lines.
  5. The system must keep a play log in agent.md: date · commit · zone · Chris's verbatim words · verdict (PASS / HOLD / KILL) · the one change. No gate passes without a verbatim quote, and the verdict must be scored against the gate's own wording from the milestone table. — m01 "good start" vs "doesn't want to stop"; no play log exists.
  6. The system must allow at most one unplayed build at a time. Adding a second system, or retuning numbers, on top of an unplayed build is blocked until a play note exists. — behavior tree + speed retune, 09-01 01:12–01:16, unplayed 21 days.
  7. The system must treat the locked milestone table as the only build queue; anything else Chris or Claude proposes mid-session goes to backlog.md with a date, and a control gets a button only when a drill needs the verb. — behavior tree not a milestone; search deferred then un-deferred; "Down + B = slide, job open".
  8. The system must require a learning line ("this build should tell us ___") per build and record the answer in the play log. — absent on every Rafter build; m03's answer was "it's unreadable" and was never written down as such.

6. Lessons → system requirements

Each is phrased for a future game-dev skill/agent system and traced to evidence above.

  1. The system must produce a locked VISION document before the first line of code — verbatim owner quotes, a numbered checklist, explicit "Not:" lines, platform + controls, a look reference image checked into the repo, and a HARD RULES block. (4.1; VISION arrived day 5; D227; D238.)
  2. The system must keep exactly one source-of-truth pointer that never moves, with every other doc marked subordinate, and must grep any "locked" design claim against the current render/rules code once before trusting it. (4.1; pointer moved 4×; D238.)
  3. The system must enforce a WIP limit of one unplayed build: it may not start build N+1 until the owner has played build N and left a note. A hard block, not a warning. (4.2; "still not played" ×6; audit T6; Lessons #2.)
  4. The system must treat the owner's play note as the only pass gate; sims, Thresh, audits and cross-play are pre-filters that can fail a build but never pass one. (4.2, 4.6; D220, D234.)
  5. The system must ask one defining question and wait for one answer before building any clone, prototype, or visual pass — and then build exactly that, with no independent verification detour. (3.3, 4.3 look spiral; D241, D239; Lessons "the one rule".)
  6. The system must gather sourced mechanics into a knowledge file before building any clone or homage, and must check the workspace's existing dossiers before inventing. (3.4; clone 8; D242.)
  7. The system must carry an inspiration map on every design — each named inspiration → the exact mechanic → where it appears on screen → which other inspiration it is felt together with in one moment — and score depth before the owner sees it. (4.5; P1 + P2 postmortems; D235.)
  8. The system must mark every rule the AI fills in as "(my call)", list them in one short block before build, and grep every restate against the VISION "Not:" lines. (4.4; D202, D232.)
  9. The system must extend spiral detection to design questions: the same open question re-answered twice, or the same owner complaint patched twice without a stated root cause, halts the loop and forces a grill. (4.3; D239; P2 patches.)
  10. The system must fix Thresh's role in writing and never renegotiate it per session: tester + coordinator + tie-breaker who plays every build before the owner; never the pen, never the director. (2; 4.7; FILE WAR; round 4.)
  11. The system must spin up parallel teams only when diversity is engineered (own-practice pitches, a banned-obvious list, no shared reading at pitch time, different models) and only for formats with proven value (cross-play review, contract-first parallel build, pitch contests). Otherwise the main thread builds solo. Agent count per session is capped and reported. (3.7-3.9; 4.7; D225, D226, D233; "11-12 agents".)
  12. The system must paste the standing hard rules into every brief it generates, generated from VISION, separated from the parts teams may challenge. (4.1; D227; Jam 4 rebuild.)
  13. The system must make background agents stop-safe: a hook or launch-time warning, and a default of foreground work for anything taste-driven. (4.10; D231, D240 "prose alone hasn't held".)
  14. The system must budget a session by "the owner has something to play", not by clock or ambition — one build per session by default, an explicit NEXT-SESSION prompt on close, no session past a stated cap. (4.11; Lessons #5; three sessions past 4 a.m.)
  15. The system must switch from tuning to rethinking after two failed loops on one complaint, and must offer a no-limit reframe ("big swings") after three small loops — early, not after eight versions. (4.3; D215; big-swings; Lessons #4.)
  16. The system must make "one bare board, proven fun, before any layer" non-skippable — or, if the owner insists on skipping, must state the specific cost in one line and get an explicit acknowledgement. (4.10; P2 "testing keeps leading to more testing" → 7 levels built blind.)
  17. The system must ship a reusable grid-game test kit: skill ladder (random < greedy < 2-ply), "bot can do what the player can", fair-enemy honesty, winnability/no-seal at spawn and per turn, phone-frame screenshot at real width, no-cache live check, and a metric-validation step against one known-good and one known-bad case before any tuning. (4.6; D219-D224, D243, D244.)
  18. The system must write a one-page postmortem for every shelved build and a distilled LESSONS file the next session reads instead of the full history, and must keep state files under a size cap (auto-archive superseded Session States). (4.8; agent.md 108 KB; dispositions 222 KB; curator never ran.)
  19. The system must convert the owner's recurring asks into acceptance criteria on the vision checklist (e.g. "a virus I can out-read", "buildings and units", "the big moment is built, not random") and report per build which are met, so an ask cannot go unbuilt seven times without being visible. (5 Lost; audit §2 "What he keeps asking for".)
  20. The system must distinguish the letter of a rule from its spirit — when an owner rule is about to structurally defeat a stated owner goal, it must flag the conflict before building. (5; P2 one-mechanic-per-level vs "influences together".)
  21. The system must log the owner's own process overrides as first-class decisions ("two changes this loop — your call", "one-change limit lifted", "skip one-board-first") so that a later postmortem can tell owner choice from AI drift without blame. (4.10.)
